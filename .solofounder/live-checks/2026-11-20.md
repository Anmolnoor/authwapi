# M1 live checks, 2026-11-20

The two M1 exit items that needed a real browser and a real mailbox. Both ran on macOS against `main` at
`fa4b4b7` (v0.3.0), the server started from source (`node src/server.ts`, `NODE_ENV` unset) on a fresh data folder.
No key, token, link or backup code is recorded here.

**Result: both PASS.** The browser QA found one security issue and six smaller ones (below); none blocks the
checklist item, which asks that every hosted page and email link works.

## Real email through Resend

`RESEND_API_KEY` set (the owner's key, passed in the server's environment only), `EMAIL_FROM=onboarding@resend.dev`,
`BASE_URL=http://localhost:4110`. A sign-up with the Resend account owner's own address: HTTP 200, no
`email failed` line in `logs/app.jsonl`, and the owner confirmed the "Verify your email" mail from
`onboarding@resend.dev` arrived in the inbox (not spam). The key did not appear in the logs. Server, data folder and
key file were deleted afterwards.

## Findings

1. **A TOTP code works more than once.** One code finished two separate password sign-ins (both
   `POST /api/auth/two-factor/verify-totp` → 200), and a code used to turn 2FA on was accepted again for the passkey
   page's fresh check. A code stays usable for about 90 seconds (one 30-second step either side). RFC 6238 §5.2 says a
   verifier must not accept a second use. Impact is low to moderate: it needs the password (or another first factor)
   and a code the user just entered. Not fixed in v0.3.0; a follow-up.
2. **Links are hard to read in dark mode.** The dark-mode styles (`src/pages.ts:51`) set no link color, so unvisited
   links use the browser's `#0000EE` on `#121212` (about 2.0:1; WCAG AA needs 4.5:1).
3. **The 2FA setup page scrolls sideways.** The `otpauth://` link doesn't wrap.
4. **No QR code on 2FA setup.** People type the key or copy the link into their app.
5. **A signed-out invitee is sent to sign in only.** `/accept-invitation` links to `/sign-in`, not sign-up, and
   asks them to open the email link again afterwards.
6. **During an app's sign-in, `/sign-in` doesn't name the app.** The consent page does, later.
7. **The logout and error pages are Better Auth's own.** The three end-session pages are unstyled. From source,
   `/api/auth/error` is Better Auth's page, with links to its docs and an "Ask AI" link, and it shows any
   `error_description` text from the URL (escaped). In the image (`NODE_ENV=production`), Better Auth redirects it to
   `/?error=…` instead, where the home page shows its generic "That link didn't work (code)" alert, worded for an
   email link, and drops any `error_description` (seen by opening `/?error=…` directly).
